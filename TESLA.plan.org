* Overview
Build a Python CLI called =tesla= that reads Tesla car and Powerwall
state through the Tesla Fleet API using
[[https://github.com/Teslemetry/python-tesla-fleet-api][python-tesla-fleet-api]]. The first use case is to watch the Powerwall
and start car charging once the Powerwall reaches 100%. More commands
will be added later.

The project is managed with [[https://docs.astral.sh/uv/][uv]] and always tracks
the latest =tesla-fleet-api= release; its current Python floor is 3.13.

* Scope (v0.1)
- Authentication against the Fleet API, usable from a headless server.
- Read-only status commands for vehicles and energy sites.
- A watch loop that polls the Powerwall and triggers =charge_start= on
  the car when the configured threshold is met.
- Manual car charging commands.
- Stage notifications via ntfy (state changes, failures, startup).
- A structure that makes adding future commands cheap.

Out of scope for v0.1 (possible follow-ups): telemetry streaming,
BLE, scheduling, multiple vehicles/sites, other notification channels,
web UI.

Steps:

1. [X] Tesla account with a verified email, owning the vehicle and Powerwall.
2. [X] Create the application, then copy the Client ID and Client Secret
   (dashboard -> View Details -> Credentials & APIs). =HomeCLI= is Active;
   Client ID/Secret are stored in =.env= (=.env.example= has placeholders):
   - OAuth grant type: *Authorization Code and Machine-to-Machine*
     (required for refresh tokens).
   - Allowed origin: =https://8cylinder.com= (scheme + host only, no
     path). It need not point at this server; in signed mode it is the
     public-key host.
   - Allowed redirect URI: =http://localhost:8085/callback= (localhost
     is exempt from Tesla's HTTPS redirect rule).
   - Scopes: the list below.
3. [X] Billing: personal use includes a $10/month credit; vehicle data and
   command calls draw it down while energy-product APIs are free. A
   payment method is only needed if usage exceeds the credit; the
   developer dashboard shows current usage. Configured as *Custom Limit
   $10/mo* with a Visa on file.
4. [ ] Developer registration and key pairing. *Registration is required
   before any Fleet API call, even read-only ones* --- =products= returns
   412 Precondition Failed until the app is registered (confirmed live in
   M2). Pairing is additionally required for signed commands:
   - Generate an EC P-256 key (=tesla key generate=, library
     =await get_private_key(path)=).
   - Host the public key at
     =https://8cylinder.com/.well-known/appspecific/com.tesla.3p.public-key.pem=.
     Keep it online permanently: registration and pairing fetch it, and
     re-pairing or adding vehicles later needs the same URL live.
   - Register the domain with Tesla (partner token via
     =oauth.partner_login()=, then
     =oauth.partner.register("8cylinder.com")=).
   - Pair the virtual key per vehicle: open
     =https://tesla.com/_ak/8cylinder.com= on a phone with the Tesla app.
   - Trust model: the private host only makes outbound HTTPS calls to
     Tesla; the public host only serves the key. Tesla and the vehicle
     use it at registration/pairing, after which the key lives in the
     vehicle's whitelist and is not re-fetched per command.
   - If pairing proves impossible, unsigned =fleet= mode remains the
     fallback.

* Headless OAuth
The server has SSH only, no browser and no public ingress. Use *manual
code paste*:

1. Register redirect URI =http://localhost:8085/callback= in the Tesla
   developer app (localhost is exempt from Tesla's HTTPS redirect rule).
2. Run =tesla auth login=; it builds the URL with
   =oauth.get_login_url(scopes)= and prints it.
3. Open that URL on any phone/laptop, log in, and authorize.
4. The browser redirects to
   http://localhost:8085/callback?code=na_...&state=... and fails to
   load --- that is expected.
5. Copy the full address-bar URL (or just the =code=) and paste it back
   into the terminal. Tesla authorization codes are short-lived; paste
   promptly.
6. The CLI extracts =code= and calls
   =await oauth.get_refresh_token(code)=, then persists =.refresh_token=
   and =.expires=. The access token itself is never written to disk.

Constructor reference (verified against 1.15.0):

#+begin_src python
TeslaFleetOAuth(session, region="na", client_id=..., client_secret=..., redirect_uri=...)
#+end_src

=TeslaFleetOAuth= subclasses =TeslaFleetApi=, so the same object is also
the API root: =oauth.products()=, =oauth.vehicles=, =oauth.energySites=,
=oauth.partner=. One session/object serves auth and calls.

Optional =tesla auth login --listen= runs a one-shot localhost callback
server for users who can =ssh -L 8085:localhost:8085 server=. Both paths
write the same token file.

Requested scopes:

#+begin_src python
["openid", "offline_access", "user_data", "vehicle_device_data",
 "vehicle_cmds", "vehicle_charging_cmds", "energy_device_data"]
#+end_src

=openid= and =offline_access= are implicit in the Authorization Code
grant. =vehicle_cmds= is included for =wake_up()=. =user_data= is
requested up front (registered in the app), removing the earlier "add
only if =products()= 403" fallback.

=~/.config/tesla/tokens.json= (mode 0600):

#+begin_src json
{"refresh_token": "...", "expires": 1234567890}
#+end_src

- Writes go to a temp file in the same directory then =os.replace=, so a
  crash cannot truncate the token file; mode is enforced 0600 on create
  and checked (with a clear error) on read.
- Tesla rotates the refresh token on every refresh, so =check_access_token()=
  usually returns a new token that must be persisted before the next call.
- =auth status= and the long-running service must not run concurrently,
  or the loser will hold a revoked token; the lock file guards this.
- Credentials precedence: CLI flag -> environment variable -> =.env= ->
  error. Secrets are never logged.
- Unknown keys and wrong types are rejected with a clear message;
  =tesla config show= prints the effective (redacted) config.

=auto-charge= flags: =--threshold N=, =--interval S=, =--dry-run=, =--once=.
=--once= performs a single evaluation pass and exits instead of looping
(logs the decision but does not sleep); =--dry-run= never sends commands.

* Core flow: auto-charge
1. Load config, acquire the lock file, refresh the access token if
   expired: =check_access_token()= returns a dict (=refresh_token=,
   =expires=) when it refreshed, else =None=; persist atomically.
   =OAuthExpired= / =InvalidToken= / =LoginRequired= -> exit 2 with a
   "re-run =tesla auth login=" message.
2. Build objects: fleet -> =oauth.vehicles.createFleet(vin)=; signed ->
   =createSigned(vin)= after =get_private_key(key_path)=; always
   =oauth.energySites.create(site_id)=.
3. Loop every =poll_interval_seconds=:
   1. =live_status()= -> =percentage_charged=; if missing compute
      =energy_left / total_pack_energy * 100=; if unavailable, log and
      continue.
   2. Below threshold -> log and sleep.
   3. At/above threshold -> read car charge state with
      =vehicle_data(endpoints=["charge_state"])= (both transports;
      =vehicle_data= is a plain read, signing only affects commands):
      - Already =Charging= or =Complete= -> exit 0, nothing to do.
      - =Disconnected= and =require_plugged= -> log "waiting for plug"
        and continue polling.
      - Otherwise wake (=wake_up()=, then poll =vehicle()= until
        =state == "online"= or =wake_timeout_seconds=), optionally
        =set_charge_limit(n)=, then =charge_start()=.
   4. Verify with a follow-up =vehicle_data= read that
      =charging_state == "Charging"= (or =Complete=), log, and exit.
4. Exit codes: 0 triggered / nothing to do, 2 config or auth error,
   3 API or vehicle error. =--dry-run= logs the decision without sending
   commands (no wake, no commands).
5. SIGINT/SIGTERM handler for clean systemd stop; single-instance lock
   file so two loops cannot run.

** decide() truth table
=auto_charge.decide(powerwall_pct, threshold, charging_state,
require_plugged)= is a pure function; the loop only performs the returned
action.

| PW reading   | charging_state      | require_plugged | Action             |
|--------------+---------------------+-----------------+--------------------|
| >= threshold | Charging / Complete | any             | =DONE= (exit 0)      |
| >= threshold | Disconnected        | true            | =WAIT_PLUG=          |
| >= threshold | Disconnected        | false           | =START= (attempt)    |
| >= threshold | Stopped / NoPower   | any             | =START= (wake first) |
| >= threshold | Asleep (read 408)   | true            | =WAIT= (do not wake) |
| >= threshold | Asleep (read 408)   | false           | =START= (wake first) |
| >= threshold | unknown / missing   | any             | =WAIT= (log, retry)  |
| < threshold  | any                 | any             | =SLEEP=              |
| missing      | any                 | any             | =SLEEP= (log)        |

* Edge cases and error handling
- =TeslaFleetError= is a =BaseException=; catch it by name, never rely on
  =except Exception=. Library errors seen in 1.15.0 include =RateLimited=,
  =VehicleOffline=, =GatewayTimeout=, =ServiceUnavailable=,
  =InternalServerError=, =OAuthExpired=, =InvalidToken=, =LoginRequired=,
  =InvalidScope=, =NotFound=, =MobileAccessDisabled=.
- 429 / transient errors: exponential backoff with jitter (5 s, x2, cap
  300 s, +/-20%), capped at 5 consecutive failures; reset the counter on
  success. Inspect =tesla_fleet_api.exceptions= for new subclasses during
  implementation.
- Auth faults (401/403): refresh once; if that fails, exit 2 with the
  =tesla auth login= hint. =InvalidScope= exits 2 and names the missing
  scope (e.g. =vehicle_cmds= for wake).
- Expired/revoked refresh token: actionable message to re-run
  =tesla auth login=.
- Vehicle asleep or unreachable during wake: timeout, then retry on the
  next cycle in watch mode; error in =--once= mode.
- =live_status= 408/timeout (gateway offline): log and keep polling.
- Never call =charge_start= unless the threshold condition is true; never
  re-send once charging; =NoPower= / =Disconnected= -> wait, do not spam
  commands.
- =~/.config/tesla/notify_state.json= (0644, non-secret) stores the last
  notified situation, the last-run time, and event cooldowns; legacy or
  malformed files degrade to empty state. =tesla notify reset= deletes it.
- Notifications are best-effort: a failed publish is logged and ignored.
  Condition messages fire only on a situation change, with an =on_start=
  snapshot on process start (resident) or after a gap (timer); events are
  always sent, with =trigger_failed=/=poll_failed= rate-limited.
- Lock file: =~/.config/tesla/auto-charge.lock= holds a PID. A live PID ->
  exit 2; a stale PID (process gone) is replaced; the lock is released on
  SIGINT/SIGTERM.

* Deployment
README documents:

- A systemd *timer* + oneshot service (recommended, since the loop
  triggers once and exits 0): =tesla-auto-charge.timer= (=OnBootSec=2min=,
  =OnUnitActiveSec=5min=, =Persistent=true=) runs
  =tesla-auto-charge.service= (=Type=oneshot=,
  =ExecStart=%h/.local/bin/tesla auto-charge --once=,
  =WorkingDirectory=%h/tesla=); =loginctl enable-linger= keeps it alive
  without login; logs via =journalctl --user -u tesla-auto-charge=; the
  lock file prevents overlap.
- Optional resident service: =ExecStart=%h/.local/bin/tesla auto-charge
  --log-file %h/.local/state/tesla/auto-charge.log= with
  =Restart=on-failure=, =RestartSec=60=, =StartLimitIntervalSec=300=,
  =StartLimitBurst=3=, plus hardening (=NoNewPrivileges=, =PrivateTmp=,
  =ProtectSystem=strict=, =ReadWritePaths=%h/.config/tesla=). It exits 0
  after a trigger, so =Restart=on-failure= does not re-arm it --- use
  =Restart=always= with =RestartSec=300= or prefer the timer above.
- The headless authentication walkthrough.
- A cron alternative: hourly =tesla auto-charge --once=.
- The refresh-token rotation caveat: do not run =auth status= while the
  service is running.

** NEXT M8 --- Charge on Solar gate mode
Keep *Charge on Solar* enabled and app-managed in the Tesla app; the loop
only flips the charge switch (=charge_start= / =charge_stop=) so CoS can
work only when the Powerwall is ready. CoS and the switch are
independent: a stop is sticky (=user_stopped=) and does not disable CoS,
so the loop mirrors the manual app taps exactly. v1 never toggles the
CoS setting from the CLI; it only reads it.

*Locked decisions:*
- Start when the Powerwall reaches 95%
  (=auto_charge.threshold= set to =95=; the default stays 100 for
  backward compatibility, gate mode is opt-in).
- Stop margin 5% (=auto_charge.stop_margin= of =5.0=): latch charging
  off once the Powerwall falls below 90%.
- Gate mode is opt-in: set =auto_charge.charge_on_solar= to =true=.
- Car SOC below the CoS lower limit at a start decision -> =WAIT= +
  alert (never start into "any source" charging).
- Latch only when the Powerwall is below the stop floor, *not* on every
  insufficient-solar pause: between 90 and 95 CoS pauses/resumes on its
  own, so the Powerwall can use the low sun to finish topping up.
- CoS remains enabled in the app; the loop never calls
  =update_charge_on_solar=.

*Loop behavior (priority order, first match wins):*
| Condition                                         | Action             |
|---------------------------------------------------+--------------------|
| CoS disabled                                      | WAIT + alert       |
| Disconnected                                      | IDLE               |
| Complete / SOC >= CoS upper limit                 | IDLE               |
| =charging_on_anything= (grid/Powerwall)             | STOP + alert       |
| Charging/Starting, PW < 90                        | STOP (latch)       |
| Charging/Starting, PW >= 90                       | IDLE               |
| =no_charge_recommended= + =POWERWALL_CHARGE_PRIORITY= | IDLE               |
| =no_charge_recommended= (other), PW < 90            | STOP (latch)       |
| =no_charge_recommended= (other), PW >= 90           | IDLE (CoS resumes) |
| =waiting_for_server=, PW < 90                       | STOP               |
| =waiting_for_server=, PW >= 90                      | IDLE               |
| =user_stopped=, PW >= 95                            | START              |
| Stopped/NoPower, PW >= 95, SOC < CoS lower        | WAIT + alert       |
| Stopped/NoPower, PW >= 95                         | START              |
| Stopped/NoPower, PW < 95                          | IDLE               |
| Asleep / unknown                                  | WAIT               |

*CoS state source:*
- Live state is
  =charge_state.managed_charging_state.charge_on_solar_state= with
  =no_charge_recommended.reason= in {=INSUFFICIENT_SOLAR=,

* Risks and open items
- *Python floor follows the library.* We always run the latest
  =tesla-fleet-api= (>= 3.13 required today); =uv= pins the interpreter
  per project, so the host's system Python is irrelevant. When the
  library raises its floor, bump =.python-version= and =requires-python=
  and relock.
- *Signed commands require a publicly hosted key.* Tesla requires
  =https://8cylinder.com/.well-known/appspecific/com.tesla.3p.public-key.pem=
  before a vehicle pairs the virtual key. =8cylinder.com= is available, so
  =signed= is the default and M3 sets it up; =fleet= remains a fallback
  for older vehicles or if pairing fails. =vehicle.fleet_status([vin])=
  reports whether the car accepts the partner key.
- *Documentation drift.* Verified against 1.17.2: =Scope= is a =StrEnum=
  in =tesla_fleet_api.const= (not exported top-level);
  =get_refresh_token()= returns =None= and silently ignores a non-OK
  response; the refresh path raises =ValueError=, not =TeslaFleetError=;
  =VehicleSigned= signs via the universal-message path and =_command()=
  auto-handshakes, so no explicit handshake call is needed --- confirm on
  the first live command in M6.
- *Empty-POST Content-Type bug.* =TeslaFleetOAuth._request= defaults
  =json=None= while the base class defaults ={}=, so bodyless POSTs
  (=wake_up()=, unsigned =charge_start()=/=charge_stop()=) go out without
  =Content-Type: application/json= and Tesla rejects them ("The HTTP
  request does not have a Content-Type header set to application/json").
  =build_oauth()= wraps the request so =None= becomes ={}=; 1.17.2 is
  the latest release, so drop the workaround once upstream fixes it.
- *Unsigned command longevity.* Tesla is steering integrations toward
  signed commands / Fleet Telemetry; =fleet= mode may be deprecated
  eventually. Keep the transport toggle thin so a switch is cheap.
- *Scope uncertainty.* =wake_up= is believed to need =vehicle_cmds=;
  confirm on first live command. =products= needed partner registration,
  not a scope change. Partner tokens need =vehicle_device_data= for
  =partner_accounts/public_key= (=openid= alone returns 403), while
  =register= works with =openid=.
- Confirm =percentage_charged= is present in your site's =live_status=
  during implementation; the energy-ratio fallback covers it if not.
- *Refresh-token rotation races* between the service and manual commands;
  mitigated by the lock file and the "no concurrent =auth status=" rule.
- Project name =tesla= collides with an existing PyPI name; irrelevant
  unless the package is published (executable stays =tesla=).
- Charging commands are not idempotent; the loop starts charging at most
  once and exits.
